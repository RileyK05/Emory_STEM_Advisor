# Runtime and boundary audit

Read-only review of the backend runtime and deployment paths named in this audit. This report is implementation evidence, not release approval. Statuses distinguish reproducible control-flow defects from behaviors that looked suspicious but match the contract.

## Confirmed bugs

### RT-01 — Conversation abandonment can deadlock with a one-slot DB pool

- **Status:** Confirmed bug
- **Severity:** Medium (requests to abandon a turn with an associated job cannot complete under this supported pool configuration)
- **Trigger and impact:** Set `DB_POOL_MAX_SIZE=1` and call `POST /api/conversations/{conversation_id}/turns/{request_id}/abandon` for a request whose `job_id` is set. The request-scoped `Conn` remains borrowed until FastAPI finishes the handler. After committing the conversation fence, the handler calls `JobStore.cancel`; that store opens a fresh connection through the same default pool. The only slot is still held by the request, so the second borrow waits until pool timeout. The route catches `JobNotFound`, not `PoolTimeout`, so the request fails instead of cancelling the job.
- **Evidence:** [`conversation_routes.py`](../../backend/app/api/routes/conversations.py#L78) accepts the request-scoped `conn`, then calls `_job_store(request).cancel(...)` at line 86. [`deps.py`](../../backend/app/api/deps.py#L37) closes that connection only in the dependency's `finally` at line 59; `request_job_store` uses the default connector at lines 95–104. [`JobStore`](../../backend/app/jobs/store.py#L84) opens a fresh connection per transaction, while [`connection.py`](../../backend/app/db/connection.py#L126) uses the default pool unless pooling is disabled. Pool size 1 is explicitly valid in [`config.py`](../../backend/app/config.py#L76) and `DB_POOL_MAX_SIZE` accepts zero through 200 at line 111.
- **Reproduction/check:** Confirmed by control-flow inspection; this route-level failure was not reproduced. Add an API integration test with a temporary migrated database and pool size 1, enqueue a conversation job, then call abandon. The current control flow attempts a second default-pool borrow before the request dependency releases its connection. Existing conversation-abandon tests exercise the state fence, but not this pool-size boundary; `test_connection_pool.py` covers bootstrap release for run routes, not the conversation path.
- **Recommendation:** Avoid nesting a store-owned borrow while the request dependency holds the same one-slot pool. Use a transaction/connection strategy that preserves the lock ordering, or a separately named bounded pool role for the cancellation operation.

### RT-02 — Tool-enabled query can self-starve a one-slot DB pool

- **Status:** Confirmed bug
- **Severity:** Medium (tool-enabled query requests cannot execute tools under this supported pool configuration)
- **Trigger and impact:** Set `DB_POOL_MAX_SIZE=1`, enable tools with an evaluated route, and submit a query that invokes a tool. `/api/query` keeps its request connection borrowed for the whole handler. The tool path commits the current transaction before model I/O, but commit does not return a pooled connection. On a tool call, `ToolExecutionLedger` requests a fresh connection from the same default pool. That borrow waits for the still-held request connection; `PoolTimeout` is not among the tool controller's translated ledger exceptions and reaches the API as an internal failure. The synchronous saved-conversation endpoint calls this same `query_response` with its request-scoped connection, so `POST /api/conversations/{conversation_id}/turns` has the same pool-size failure (mapped to a safe 503 by its outer handler). The streaming conversation worker uses a separately named `conversation_execution` pool, so this finding does not extend to that path.
- **Evidence:** [`routes.py`](../../backend/app/api/routes/corpus.py#L95) passes the dependency-provided `conn` into `query_response`; [`deps.py`](../../backend/app/api/deps.py#L37) retains it until the request completes. [`query_service.py`](../../backend/app/api/query_service.py#L122) constructs the ledger from `connector(settings, conn.info.dsn)` at lines 142–143; `connector` defaults to the shared `default` pool ([`connection.py`](../../backend/app/db/connection.py#L126)). [`ToolExecutionLedger`](../../backend/app/tools/executions.py#L52) opens a fresh connection per transition, and [`controller.py`](../../backend/app/generation/controller.py#L164) catches typed ledger errors but not `PoolTimeout`. The synchronous conversation caller passes the same `conn` at [`conversation_routes.py`](../../backend/app/api/routes/conversations.py#L267) and line 307; the worker's separate role is configured in [`scripts/worker.py`](../../backend/scripts/worker.py#L93).
- **Reproduction/check:** Confirmed by control-flow inspection across direct and synchronous-conversation callers; neither route-level failure was reproduced. Add a focused API integration test with a temporary migrated database, `DB_POOL_MAX_SIZE=1`, tools enabled, and a fake provider that returns one valid tool call. Assert the current handler blocks until pool timeout rather than completing the tool call. Existing connection-pool tests cover distinct worker roles and bootstrap borrowing, but do not cover this request-plus-ledger path.
- **Recommendation:** Ensure tool ledger transitions do not require a second borrow from the pool held by the HTTP request, or configure and validate a separate pool role for the ledger. Add a size-1 regression test.

## Intentional and correct behavior

### RT-03 — Provider and route selection are gated before credentials are used

- **Status:** Intentional correct
- **Severity:** Informational
- **Evidence:** [`runtime.py`](../../backend/app/runtime.py#L41) builds the configured static provider through the factory and records only an exception type when construction fails. [`selection.py`](../../backend/app/connections/selection.py#L69) requires routing to be explicitly enabled and an eval-suite hash; it commits the route-profile read before provider construction and does not fall back to environment credentials when routing is enabled. [`registry.py`](../../backend/app/connections/registry.py#L40) checks enabled/evaluated status, role, data scope, and capabilities before decrypting credentials in `_get` at line 118. The query caller requires private-workspace scope for OIDC workspaces and fails closed when private routing is disabled ([`query_service.py`](../../backend/app/api/query_service.py#L97)).
- **Why it looked suspicious:** Provider construction errors are swallowed at startup and a static provider can be absent. The downstream query path makes model availability an explicit 503, while retrieval refusals and non-generation inspection remain available by design.
- **Checks:** Existing runtime, connection, selection, and routing tests cover factory use, eval/scope gates, no environment fallback, and current-profile checks. No live provider was invoked.

### RT-04 — Development identity, local administration, and sandbox boundaries fail closed

- **Status:** Intentional correct
- **Severity:** Informational
- **Evidence:** `scripts.serve` binds to `127.0.0.1` by default ([`serve.py`](../../backend/scripts/serve.py#L16)); development auth rejects forwarded requests and non-loopback Host headers ([`dependencies.py`](../../backend/app/auth/dependencies.py#L11)) and `AuthService.resolve` independently rejects non-loopback client addresses ([`service.py`](../../backend/app/auth/service.py#L254)). Local connection administration additionally checks the actual client address and loopback Host/Origin ([`connection_routes.py`](../../backend/app/api/routes/connections.py#L72)). Production sandbox execution requires a separately attested worker and `runsc` ([`types.py`](../../backend/app/sandbox/types.py#L54)); the worker deployment binds its port to loopback, and the remote client checks HTTPS, worker readiness, `runsc`, host attestation, and immutable image IDs ([`remote.py`](../../backend/app/sandbox/remote.py#L78), [`compose.worker.yaml`](../../sandbox/compose.worker.yaml#L2)). The runbook clearly states that attestation is operator-provided and deployment scaffolding is not isolation proof ([`WORKER.md`](../../sandbox/WORKER.md#L1)).
- **Why it looked suspicious:** Development authentication is the default, and the sandbox host separation value is an environment attestation. The serving script defaults to loopback, both the Host and peer address are checked, and the sandbox documentation labels attestation as an operator handoff rather than runtime proof.
- **Checks:** Auth and sandbox unit coverage exists. This audit did not start a server, contact an identity provider, or run a container.

### RT-05 — Similarity graph implementation matches the fixed department/topic/course tree

- **Status:** Intentional correct
- **Severity:** Informational
- **Evidence:** [`build.py`](../../backend/app/simgraph/build.py#L1) documents that course vectors are temporary clustering inputs and that no course-to-course edges are persisted. `department_tree` partitions course rows by fixed subject-to-department membership before clustering each department independently (lines 129–150). [`view.py`](../../backend/app/simgraph/view.py#L1) emits containment edges only; [`walk.py`](../../backend/app/simgraph/walk.py#L1) returns groups from topic/department traversal and disclaims prerequisite sequencing. The architecture contract states fixed departments → learned topic groups → course leaves and no lateral similarity links ([`architecture.md`](../architecture.md#L15)).
- **Why it looked suspicious:** Cosine distance and hierarchical clustering can suggest a course-to-course similarity graph. Here those distances are used only to build within-department topic containment, matching the user’s graph contract.
- **Checks:** Existing `test_simgraph.py` exercises fixed-boundary nudges and tree behavior. No graph build or database mutation was run for this audit.

## Verification and scope

Read `AGENTS.md`, the relevant runtime, provider, connection, auth, API, database, backup, sandbox, Compose, and similarity-graph implementation, plus architecture sections on providers/routing, identity/scope, sandboxing, deployment, and backups. Also inspected relevant test names and code paths. No live database tests were run.
